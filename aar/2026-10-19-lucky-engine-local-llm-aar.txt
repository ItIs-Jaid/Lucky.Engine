# AAR — Local LLM Compute on the Tailnet and a Controlled A/B Evaluation of Lucky.Engine

**Document type:** After-Action Review / technical evaluation report
**Date:** 2026-10-19
**Scope:** Two Linux tailnet nodes used as local inference compute; four LLMs served by Ollama; a controlled comparison of Lucky.Engine's context-selection framework against an unfiltered full-context baseline, run on both a private corpus and a public corpus.
**Status:** Benchmark complete. Framework defect identified and documented; not yet remediated.

> **Redaction note.** Per the standing rule that publishable documents must not carry operator identifiers, two things are abstracted throughout this report: (a) all personal facts retrieved during the private-corpus trial are described structurally (`destination A` vs `destination B`, `superseded numeric figure`) rather than quoted, and (b) all network addresses and filesystem paths are placeholdered. The raw evidence files remain local and are explicitly marked private. The publication gate was run against the public artifacts and returns CLEAN (Section 6).

---

## 1. Abstract

We asked a simple question with an uncomfortable answer: *does Lucky.Engine's context-selection layer actually help an agent answer questions, or does it only make the prompt smaller?*

Two Linux machines on a private tailnet were provisioned with Ollama and model weights (four models total, 1.3–4.9 GB). We then ran a 2-arm, within-subject benchmark: Arm A receives the ~50–290-token context pack that the framework selects; Arm B receives the entire relevant corpus (~760–2,880 tokens). Same model, same questions, same decoding parameters, deterministic sampling, graded against facts known to exist in the corpus.

Across **30 measured trials** (24 private-corpus, 6 public-corpus on the server; 18 public-corpus on the data node), the framework delivered a consistent **7.5×–9.9× reduction in prompt tokens** and **3.5×–10× lower latency**, but **lost accuracy**, capping at 43–62% versus 71–100% for the unfiltered arm.

The root cause is not the compression. It is that **the framework selects node *labels* whose *content* is stale or absent.** A smaller prompt is only a win if it still contains the answer. It did not.

## 4. Method

### 4.1 Design

A **within-subject, 2-arm, paired design**. Every question is asked twice of the same model instance: once with the framework's selected context, once with the full corpus. Order is fixed (framework first) to prevent the full-context arm warming the cache for the small arm. Temperature 0.0, `num_predict` 80–120, `num_ctx` 4096–8192.

### 4.2 Corpora

**Private corpus (trial 1).** The agent's own memory: SSOT, digest, human-readable summary, and skills index — 9,677 characters (~2,419 tokens). Chosen because it contains facts the model cannot know otherwise, and because its ground truth is externally verifiable.

**Public corpus (trial 2).** `public/catalog.json` only: 37 generic skill names with group/source attribution, plus 5 upstream source repos — 2,973 characters (~743 tokens). Contains no operator identifiers by construction.

**A discarded third corpus.** An initial attempt used the full 8,276-node graph as the "no framework" baseline. Inspection showed that graph carries **zero node content** — `content`, `description`, and `summary` are null on all 8,276 nodes; only `id`, `label`, `community`, `source_file` exist. The arm was therefore feeding the model a list of bare labels, and it correctly answered "I don't have access to that information." That arm was **discarded as invalid**, not reported as a framework win. This is recorded because the corrected baseline is what makes the result honest.

### 4.3 Arms

| Arm | Context supplied | Assembly |
|---|---|---|
| **Framework** | Lucky.Engine node pack, budget 500 tokens | `engine.resolve_query(q, budget=500)`, labels + content |
| **No framework** | Entire corpus verbatim | single system message |

For the public trial the engine was pointed at an **isolated public bridge** (`public_graph.json`, 42 nodes, no `bridge_nodes.json`) so that no private skill-to-memory mapping could leak into the pack. This was necessary: the first public run pulled private bridge entries (`agent-skills → Goals` etc.) into the context. That contamination is defect D6.

### 4.4 Instrumentation

Every call is a single `POST /api/chat` with `stream: false`. The response carries the measurements natively:

| Metric | Source field | Definition |
|---|---|---|
| `prompt_tok` | `prompt_eval_count` | tokens the model actually ingested |
| `gen_tok` | `eval_count` | tokens emitted |
| `tok_s` | `eval_count / eval_duration` | decode throughput |
| `total_s` | wall clock around the request | user-perceived latency, includes prompt ingest |
| `ctx_tok` | `len(context) / 4` | context size estimate (char/4 heuristic) |

Latency is reported as **time to complete response**, not time-to-first-token, because `stream: false` was used throughout for measurement stability.

### 4.5 Grading

Deterministic string matching, case-insensitive, whitespace-stripped. Each question has 2–3 required terms drawn from the corpus. Score is `hits / expected`. No LLM judge was used — that would have introduced a second model's opinion as ground truth.

**Private questions (values redacted here):**

| ID | Asks | Required terms |
|---|---|---|
| `move_fund` | active fund + retired figure | current amount, its components, superseded figure |
| `move_plan` | deadline + top destination | deadline year, current destination |
| `tailnet` | storage node + its address | node role, address |

**Public questions:**

| ID | Asks | Required skills |
|---|---|---|
| `review` | skills covering code review | code-review-and-quality, requesting-code-review, receiving-code-review |
| `planning` | skills for planning and specs | brainstorming, writing-plans, spec-driven-development |
| `agents` | skills orchestrating parallel agents | dispatching-parallel-agents, subagent-driven-development |

### 4.6 Threats to validity

1. **Small n.** 3 questions per corpus, 6–18 trials per configuration. Directional, not statistically powered.
2. **Weak models.** 1B and 3B are poor instruction-followers independent of context quality. The 1B model answered `NO` to "reply with the single word READY."
3. **Prompt caching.** Ollama caches the shared prompt prefix; the second and third full-context calls in a series are much faster than the first. The first call is the honest uncached figure and is reported separately.
4. **Char/4 token estimate** drifts from the model's real tokenizer. `prompt_tok` (measured) is authoritative; `ctx_tok` is indicative only.
5. **Fixed arm order** prevents cache contamination in one direction but cannot rule out model warm-up effects favouring Arm B.

## 6. Defects Found

All seven were found by execution, none by reading.

| ID | Location | Defect | Effect | Status |
|---|---|---|---|---|
| **D1** | `benchmark.py:11–13` | literal `<your-name>` placeholder paths | immediate `OSError`, benchmark unrunnable | **fixed** |
| **D2** | `engine.py:881` | nested same-quote f-string | `SyntaxError` on Python 3.9 (both nodes) | **fixed** |
| **D3** | `engine.py:464` | `"model": "default"` hardcoded | Ollama 404 → bare `except` → **silent keyword fallback**; every "LLM" measurement was actually the rule-based router | **fixed** (env-overridable + `default` alias) |
| **D4** | `assemble_pack` | pack nodes carry `content: null` | framework arm answered `UNKNOWN` | mitigated in harness; **not fixed in engine** |
| **D5** | corpus baseline | 8,276-node graph has **0 nodes with content** | first "no framework" arm was label-only, invalid | **discarded arm**, replaced |
| **D6** | public bridge isolation | engine defaulted to private `bridge_nodes.json` | private skill→memory mappings leaked into a "public" run | **fixed** (isolated `public_graph.json`) |
| **D7** | `public_bench/bridge/.lucky_cache.json` | engine cache persists absolute home paths | **9 publication-gate findings** (`C:\Users\<name>`, handle, workspace) | **purged**, gate re-run CLEAN |

**D3 is the most consequential.** A benchmark that silently degrades from LLM to keyword matching does not measure the LLM at all. It was caught only by timing the classifier directly (4 ms is physically impossible for a network round-trip to a 3B model) and then confirming the underlying 404.

## 7. Security and Provenance Review

Conducted in response to a direct question about trusting the models.

**Provenance chain:** every weight set came from `registry.ollama.ai` via `ollama pull`; no third-party GGUF, no manual `.bin` acquisition. `~/.ollama/models/manifests/registry.ollama.ai/library/` contains only official entries.

**Integrity:** blobs are content-addressed. `llama3.1:8b` resolves to `sha256-667b0c19…6b06a29`. A single altered byte changes the digest and the model will not load.

**Stated limits:** digest proves provenance and integrity, *not* intent. There is no signing beyond TLS plus content addressing. A compromised registry would serve a plausible model whose digest you would accept because the registry asserted it.

**Actual hazard surface:** not the weights. The models are CPU-only, no network egress, no tool access, no shell — they map text to text. The real risks are (a) **prompt injection through retrieved memory**, because the framework feeds retrieved text as trusted context, and (b) **data handling**: the private trial required copying personal memory text to both nodes. That text was shredded (`shred -u`) from both machines after the run, and the private result files are flagged private and excluded from publication.

## 8. Root Cause

Three failure modes, all instances of starting before scope was settled:

**RC1 — The framework optimises the wrong quantity.** It optimises tokens. It never checks that the selected pack *contains the answer*. A 50-token pack that omits the fact scores 0; a 743-token pack that includes it scores 3/3. Compression without recall is not a feature.

**RC2 — The knowledge store is stale and partially empty.** Node content is not rebuilt from the current SSOT, so the graph asserts a superseded destination and date with high confidence. The absence of content on the tailnet node is worse than stale content, because `UNKNOWN` at least fails loudly.

**RC3 — Failures were silent.** `engine.py` caught every exception in the classifier and fell back to keywords without logging. Three separate "successful" benchmark runs were measuring the wrong subsystem. Silent fallback in a measurement path is a defect, not resilience.

---

## 9. Lessons

1. **Verify the instrument before trusting the reading.** A 4 ms "LLM call" was the tell. Time the primitive, not the aggregate.
2. **A degraded baseline is worse than no baseline.** The graph-with-no-content arm would have produced a spectacular 100%-reduction headline and been entirely false.
3. **Never bench a model that is not resident.** Preflight with `ollama ps`; cold-load seconds otherwise masquerade as framework overhead.
4. **Compression must be graded on recall, not tokens.** Every future benchmark of this framework must include an accuracy term, or it is measuring the wrong thing.
5. **Isolate the public path physically, not by intent.** D6 proved that "this code will only read public data" is not a control; a separate graph file is.
6. **Publication gates find real things.** D7 was invisible until `check_public.py` ran over the folder.
7. **Hardware ceiling dictates model choice.** 3 GB cannot host a 3B model; pretending otherwise produces OOM or swap-thrash, not results.

---

## 10. What to Move Forward With

**Recommendation: keep the framework, fix the store, and stop quoting token savings as a victory.**

| Priority | Action | Rationale |
|---|---|---|
| **P0** | Rebuild bridge node content from the current SSOT | Turns 43% into ~100%. Without this nothing else matters. |
| **P0** | Make `classify_intent_llm` log its fallback | D3-class silent degradation must be observable. |
| **P1** | Grade every future bench on accuracy *and* tokens | Prevent the metric from flattering the framework. |
| **P1** | Add a `content is None` guard that widens the pack | Prefer a larger pack over an empty answer. |
| **P2** | Raise default pack budget for multi-node answers | Public trial showed 35–68 tok under-selects; 200–300 tok needed. |
| **P2** | Ship `public_bench/` as the reference harness | It is identifier-free and reproducible. |

**Deployment guidance from the measurements:** `llama3.1:8b` on the 14 GB node is the accuracy winner (100% with full context). If the store is fixed, 8B + framework should reach the same accuracy at roughly one-third the latency. The 3 GB node should be treated as a **fallback router**, not a primary reasoner — 1B answered `NO` when asked to say `READY`.

**Do not** run the framework on the 3 GB node and claim parity; it was chosen by RAM, not by capability.

## 13. Closing

The honest one-line version: **Lucky.Engine makes prompts 8–10× smaller and answers 3–10× faster, and right now it is also less correct — not because compression is wrong, but because the thing it compresses from is out of date and sometimes empty.**

The framework is worth continuing. The token economics are real and they matter most exactly where resources are tightest. But the next commit should not be a benchmark improvement — it should be a rebuild of the node content, plus a log line the moment the LLM classifier falls back to keywords.

A tool that quietly substitutes a weaker method and reports the strong method's name will keep producing confident, wrong numbers. That is the one defect worth fixing first.
